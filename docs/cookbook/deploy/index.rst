===========================
Deploying TurboGears
===========================

This section describes how to deploy a TurboGears application with a WSGI
server behind a reverse proxy, or with Apache and ``mod_wsgi``. Application
configuration belongs in a deployment-specific ``.ini`` file; WSGI-server and
proxy configuration belongs to the deployment server.

WSGI servers that can load PasteDeploy applications can use the application
configuration generated by a TurboGears project. ``gearbox serve`` is the
standard project command for starting such a server.

#.  Create and adapt a production configuration from the project's existing
    configuration. Run deployment commands from the installed project
    directory.

    .. code-block:: bash

       $ cp development.ini production.ini
       $ python3 -m venv .venv
       $ . .venv/bin/activate
       $ python -m pip install -e .

#.  Install and configure a PasteDeploy-compatible WSGI server. The following
    is a server-specific example using Waitress; use the configuration format
    required by the WSGI server you select.

    .. code-block:: bash

       $ python -m pip install waitress

    For a public HTTPS app mounted at ``/portal``, the following Waitress
    settings trust a local reverse proxy and translate its forwarded host,
    scheme, and port:

    .. code-block:: ini

       [server:main]
       use = egg:waitress#main
       host = 127.0.0.1
       port = 8080
       url_prefix = /portal
       trusted_proxy = 127.0.0.1
       trusted_proxy_headers = x-forwarded-host x-forwarded-proto x-forwarded-port

    With this setup, the reverse proxy must forward ``/portal/...`` with the
    prefix intact. Waitress's ``url_prefix`` handles the public mount prefix
    before application routing. Replace ``127.0.0.1`` with the actual proxy
    address, and trust only a proxy that filters or replaces client-supplied
    forwarded headers.

#.  Start the WSGI server on an address reachable by the reverse proxy.
    ``gearbox serve`` reads the ``[server:main]`` section from the selected
    PasteDeploy configuration.

    .. code-block:: bash

       $ gearbox serve -c production.ini

#.  Configure the reverse proxy to forward public requests to the WSGI
    server. The proxy and WSGI server must turn trusted external request
    information into the WSGI environment, including ``wsgi.url_scheme`` and
    the public host and port represented by ``HTTP_HOST`` or
    ``SERVER_NAME``/``SERVER_PORT``. Exact forwarded-header names, trust rules,
    and server settings are server-specific. The proxy must remove or replace
    untrusted client-supplied forwarded values before passing trusted values
    to the WSGI server.

    TurboGears does not parse ``X-Forwarded-*`` headers itself. Do not add a
    TurboGears proxy setting; configure header translation and trust at the
    proxy or WSGI-server layer.

    When the application is public at a subpath, forward ``/portal/...``
    intact for this Waitress setup. Waitress's ``url_prefix`` handles the
    public mount prefix before application routing; configure the equivalent
    prefix option when using another WSGI server. Qualified URLs depend on the
    request scheme, host, and port, so those values must describe the public
    request rather than the internal proxy connection.

#.  Visit the public URL and verify that application links, redirects, and
    static-file URLs retain the public scheme, host, port, and subpath.

See :ref:`modwsgi_tutorial` for an Apache deployment that keeps the WSGI
application in a ``mod_wsgi`` daemon process.
